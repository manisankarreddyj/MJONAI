## 0. Executive Directive

MJONAI is a long-running personal AI/quantitative trading research and execution system. The central engineering principle is:

> **Do not build from scratch when a mature, compatible, maintainable existing implementation can solve the problem.**

Existing repositories, libraries, models, APIs, MCP servers, Claude Code skills, plugins, agent frameworks, research frameworks, data connectors, and infrastructure should be treated as candidate building blocks.

However:

> **Do not blindly install or adopt anything because it is popular, has many stars, or appears in this document.**

This document was generated by GPT from broad technical knowledge and research. It is a proposed blueprint, not an immutable specification. Claude Code/Ox Alpha is explicitly instructed to inspect the actual MJONAI repository, independently research current alternatives, identify newer/better components, challenge this document, and improve the final architecture.

The final system should optimize for:

- correctness;
- research validity;
- reproducibility;
- modularity;
- maintainability;
- provider/model independence;
- low unnecessary complexity;
- strong testing;
- auditability;
- data lineage;
- realistic backtesting;
- safe paper/live execution boundaries;
- low-cost experimentation;
- persistent project knowledge;
- graceful replacement of dependencies;
- and preservation of the genuinely unique MJONAI intelligence.

# 1. Non-Negotiable Principles

## 1.1 Reuse before rebuild

For every subsystem:

1. Search existing open-source implementations.
2. Search official SDKs/APIs.
3. Search mature Python libraries.
4. Search academic implementations.
5. Search MCP/agent/skill ecosystems where relevant.
6. Compare candidates.
7. Check license and security.
8. Check maintenance/activity.
9. Test compatibility.
10. Only then decide whether custom implementation is justified.

## 1.2 Build only what creates MJONAI-specific value

Potentially reusable:

- data ingestion;
- indicators;
- standard forecasting models;
- standard portfolio mathematics;
- generic backtesting;
- generic agent orchestration;
- generic MCP;
- standard experiment tracking;
- broker SDK communication;
- generic storage;
- standard observability.

Potentially unique MJONAI assets:

- market-state interpretation;
- opportunity detection;
- signal fusion;
- confidence model;
- capital allocation philosophy;
- strategy selection;
- regime-conditioned decision logic;
- execution policy;
- learning/evaluation loop;
- proprietary feature combinations;
- decision/audit schema;
- orchestration logic that meaningfully improves outcomes.

## 1.3 Provider independence

No core business logic should depend directly on one:

- LLM provider;
- gateway;
- API router;
- market-data provider;
- broker;
- forecasting model;
- agent framework.

Use adapters/interfaces.

## 1.4 Project-owned persistence

Important knowledge must live inside or alongside the MJONAI repository in portable, version-controlled formats.

Changing:

- Claude Code;
- Claude desktop;
- Claude CLI;
- OpenRouter;
- Ox Alpha;
- another gateway;
- another model;
- another IDE;
- another agent framework;
- or reinstalling the development environment

must not erase project knowledge.

## 1.5 Reproducibility

Every meaningful research result must be traceable to:

- code version;
- data version;
- configuration;
- model/version;
- feature set;
- parameters;
- random seed where applicable;
- execution assumptions;
- timestamp;
- environment;
- evaluation method.

## 1.6 No look-ahead leakage

Financial research must explicitly prevent:

- future information leakage;
- survivorship bias;
- selection bias;
- data snooping;
- overlapping-label contamination;
- improper normalization;
- future corporate-action leakage;
- unrealistic execution assumptions.

# 3. Decision Framework for External Technology

Every candidate should be classified as one of:

- **ADOPT** — use as-is.
- **ADAPT** — integrate with a thin MJONAI adapter.
- **WRAP** — expose behind a stable MJONAI interface.
- **FORK** — fork only when necessary and justified.
- **VENDOR** — copy a small stable component only when licensing permits and long-term control is needed.
- **WATCH** — promising but not ready.
- **REJECT** — unsuitable.
- **BUILD** — custom implementation is justified.

Use this evaluation:

| Criterion | Questions |
|---|---|
| Functional fit | Does it actually solve our requirement? |
| Correctness | Is the implementation technically sound? |
| Financial validity | Is it appropriate for financial use? |
| Maintenance | Is it actively maintained? |
| Release quality | Are releases/tests/documentation credible? |
| Community | Is there meaningful adoption? |
| License | Can MJONAI legally use/distribute it? |
| Security | Any supply-chain or credential risks? |
| Performance | Does it meet actual workload requirements? |
| Python/runtime | Does it fit the MJONAI environment? |
| Windows | Does it work in the current development environment? |
| GPU | Does it require/benefit from CUDA? |
| Extensibility | Can it be adapted without invasive changes? |
| API quality | Is integration clean? |
| Lock-in | Can MJONAI replace it later? |
| Reproducibility | Can runs be reproduced? |
| Operational maturity | Is it appropriate beyond a demo? |
| Migration cost | How hard is adoption? |
| Existing overlap | What current MJONAI code can it replace? |
| Strategic value | Does it reduce long-term engineering burden? |
