## 6. RISK MANAGEMENT SYSTEM

Philosophy: capital protection first; dynamic sizing; every trade carries defined risk; portfolio carries hard limits and kill switches.

- **Sizing:** Size = (capital × risk_pct × market_weight × confidence_weight) ÷ stop_distance. Risk caps: INTRADAY 1.0% / SWING 1.5% / POSITIONAL 2.0% / options-buying 0.5% (the 0.5% options cap is defined but **not reachable** via the current timeframe→risk map, which defaults options to SWING 1.5%). Market weight scales down with VIX (real Wilder ADX in `indicators.py` — the H5 pseudo-ADX defect was fixed in G2). Anchored to static `TOTAL_CAPITAL`, not live equity.
- **Stops:** structure- or ATR-based, never arbitrary %. Stages INITIAL → BREAKEVEN (after 1R) → TRAILING. Never overridden once set. **Note (2026-10-09):** the runner trail now uses the entry-time stop distance (`entry − initial stop_loss`), which scales with the instrument's volatility via the strategy's own stop geometry; the trades table does not persist a raw ATR, so a literal 2.5×ATR trail is not yet wired.
- **Tranches:** 3-part partial exits with per-tranche targets; parent-row settlement rolls closed-tranche P&L (fixed in G1).
- **Hard limits ladder:** soft stop (3 consecutive losses → 120-min halt) → daily cap (≤2 new trades non-RESEARCH) → daily risk stop −3% (VIX-scaled) → **kill line −15% drawdown → square off ALL + lockout**. Drawdown tiers ≥5%/10%/15% → advisory / halve sizes / hard kill.
- **Emergency protocols:** earnings blackout (fail-closed non-RESEARCH, Gate 2) + behavioral guard (2 losses→30m pause; same-symbol×2→45m; 4 losses→day lockout; post-14:30 loss stop), broadcast via Telegram/Discord + `risk_events`. **Honest correction (2026-10-09):** crisis-mode / Union-Budget / RBI-MPC blackouts (former `risk/special_modes.py`) were dead code — never called in the engine — and were **removed**; only the earnings blackout is enforced today.
- **Kill-line semantics (P0.6 repaired 2026-09-20):** session circuit (≥15% drawdown from the session peak anchored to yesterday's close, **arms in any non-RESEARCH mode** — LIVE and PAPER) **plus** lifetime ruin protection (equity ≤85% of the persisted lifetime peak watermark from `save_peak_equity`/`load_peak_equity`, monotonic, manual-reset only). Both fire auto-liquidation and block all trading; RESEARCH never arms (exploratory equity must not lock the operator). Previously the code armed the kill line in LIVE only, and the lifetime-ruin half of the doc was fiction — `save_peak_equity`/`get_current_drawdown_pct` were imported but never called in the monitoring loop.

### 11.1 Backups (tiered archive engine — rebuilt 2026-10-13)

**`tools/scripts/backup_database.py` is a filesystem archive engine, and it does NOT back up Supabase.** It reads local files under `storage/` and zips them into `backups/`; it never opens a database connection, never calls the REST client or the pooler, and has no `SUPABASE_*` handling at all. The only Supabase dump on record is the manual 2026-08-25 pre-reset export (`supabase_FULL_backup_20260825_105616.jsonl`, 195,897 rows, referenced in §11 above and kept outside this repo). **A DB backup must be run separately** (e.g. a `pg_dump`/Supabase CLI export) — trusting `backup_database.py` to cover the ledger would be a data-loss assumption with nothing behind it.

**Two tiers, each independently bounded** (prefixes keep the generations from interfering with each other's retention):

| Tier | Prefix | Contents | Retention bounds |
|---|---|---|---|
| `state` | `mjonai_state_` | runtime journals (`*.jsonl`), `behavioral_guard_state.json`, `heartbeat.json`, `storage/research/`, `storage/research_evidence/` | 30 days · 30 copies · 256 MB |
| `data` | `mjonai_data_` | `storage/parquet/**` warehouse only | 60 days · 4 copies · 8 GB |

**Deliberately excluded:** `storage/models/` (1.47 GB of reproducible HuggingFace weights), `storage/vendor/` (git clones), `cache/`, `logs/`, `datasets/`, `duckdb/`, and the root `.env`. The models/vendor exclusion is fail-closed in code (`_EXCLUDED_TOP_LEVEL`), not a convention — a large re-downloadable asset can never silently re-enter an archive. This is the fix for the 2026-10-13 disk finding: the previous script was a **full snapshot per run with no tier, no exclusions and no working prune**, so `tests/test_backup_database.py` calling `backup_data_and_state(retention_days=14)` created one ~2 GB archive per test run until **`backups/` reached 76.86 GB (66 ZIPs) on a drive with 6.6 GB free**.

**Safety contract (all regression-pinned in `tests/test_backup_database.py`):**
- **Atomic** — written to `*.part` then promoted with `os.replace`; a crash mid-write leaves only a `.part`, which the next run sweeps.
- **Exclusive lock** — a `.backup.lock` in the backup root serialises runs (stale after 6h); *a refused run never releases a lock it does not own*.
- **Space guard** — the projected payload is checked against free disk **before** any write (2× multiplier), so a backup can never be the thing that fills the drive.
- **Fail-closed destination** — the live root `backups/` is only reachable when `allow_default_destination=True` (CLI only). Library callers must pass an explicit `backup_root`, which is what keeps the test suite from ever writing into the live directory.
- **Retention is bounded by age AND count AND bytes**, applied both before and after a write; unspecified bounds fall back to the tier default rather than being silently disabled, and the newest archive of a tier is never pruned away to zero.

Run it from the repo root: `python tools\scripts\backup_database.py --tier state` (add `--tier data`, `--dry-run`, `--no-prune` as needed).
